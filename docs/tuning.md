# 웹캠 판정 기준 조정 기록

어려웠던 구간 감지와 감점이 웹캠 수준의 시선 오차에서도 공정하게 동작하도록 기준을 조정한 기록입니다. 실제 웹캠 데이터가 아니라 **시뮬레이션**으로 조정했으므로, 실제 세션이 쌓이면 다시 확인해야 합니다(아래 "다음 단계").

## 방법

`backend/sim.py`는 정답을 아는 가상 독자를 만듭니다.

- **독자 모델**
  - 단어마다 고정합니다. 고정 시간은 로그정규분포를 따르고 평균은 230ms입니다.
  - 짧은 단어는 건너뛰고, 긴 단어는 다시 고정하고, 가끔 짧게 되돌아갑니다.
  - 정해 둔 문장 중 일부는 1.8~2.6배 느리게 읽고, 일부는 다음 문장을 읽은 뒤 1~2번 되돌아가 다시 읽습니다.
- **트래커 모델**
  - 30Hz로 샘플링합니다.
  - 보정 후 남는 고정 오프셋(검증 오차)이 있습니다.
  - 프레임 간 흔들림이 있습니다. WebGazer의 칼만 필터를 흉내 내 AR(1)로 서로 상관된 잡음으로 만들었습니다.
  - 머리 움직임으로 생기는 느린 드리프트가 있습니다.
  - 얼굴을 놓쳐 샘플이 잠깐 끊기는 구간이 있습니다.
- **지문**: 기본 지문 "Achtung, schwarze Katze!?"를 실제 화면과 같은 글꼴 크기, 줄 간격, 폭으로 배치했습니다(403단어, 44문장).

`tools/tune.py`가 두 종류의 독자로 측정합니다.

- **어려움 없는 독자**: 어떤 문장도 어렵지 않았던 독자입니다. 이 독자에게 붙은 표시와 감점은 모두 잘못된 것입니다.
- **어려움 있는 독자**: 느린 문장 2개와 다시 읽은 문장 2개가 있습니다. 얼마나 찾았는지(재현율)와 찾은 것 중 맞은 비율(정밀도)을 봅니다.

조정은 시드 0–9의 독자로 했고, 아래 결과는 조정에 쓰지 않은 시드 500–523의 독자 24명씩으로 측정했습니다.

```bash
python -m tools.tune baseline   # 현재 기준으로 오차 수준별 측정
python -m tools.tune sweep      # 기준값 탐색
python -m tools.tune report     # 조정에 쓰지 않은 독자로 최종 측정
```

## 결과

오차 수준은 보정 화면이 보여 주는 평균 오차 기준입니다.

**조정 전**(2단계 기준값)

| 조건 | 정밀도 | 재현율 | 어려움 없는 독자의 잘못된 표시 | 어려움 없는 독자의 감점 | 문단 커버리지 |
|---|---|---|---|---|---|
| 이상적 | 1.00 | 0.98 | 0 | 0 | 0.80 |
| 좋음 (≈50px) | 0.14 | 0.79 | 18.4문장 | 21.8점 | 0.67 |
| 보통 (≈100px) | 0.11 | 0.88 | 30.3문장 | 25점(상한) | 0.43 |
| 나쁨 (≈160px) | 0.14 | 0.52 | 13.3문장 | 14.8점 | 0.14 |

웹캠 잡음 때문에 시선이 한 줄쯤 위아래로 흔들리면, 앞 문장으로 "되돌아간" 것처럼 보였습니다. 그래서 어려움 없이 읽은 학생도 거의 모든 문장이 표시되고 감점 상한을 받았습니다. 잡음 때문에 고정이 잘게 끊기면서 문단 커버리지도 크게 떨어졌습니다.

**조정 후**

| 조건 | 정밀도 | 재현율 | 어려움 없는 독자의 잘못된 표시 | 어려움 없는 독자의 감점(계산상) | 어려움 있는 독자의 감점(적용) | 문단 커버리지 |
|---|---|---|---|---|---|---|
| 이상적 | 0.98 | 0.84 | 0.04문장 | 0.1점 | 7.2점 | 0.79 |
| 좋음 (≈50px) | 0.52 | 0.38 | 0.71문장 | 0.7점 | 3.5점 | 0.70 |
| 보통 (≈100px) | 0.41 | 0.31 | 1.46문장 | 1.3점 | 1.9점 | 0.70 |
| 나쁨 (≈160px) | 0.19 | 0.28 | 4.04문장 | 3.8점 | 0.2점(보류) | 0.68 |

- 어려움 없는 학생이 받는 감점이 25점에서 1점 안팎으로 줄었습니다.
- 문단 커버리지는 오차 수준과 관계없이 0.7 전후로 유지됩니다. 웹캠이 좋지 않다고 점수가 깎이지 않습니다.
- 대신 오차가 있을 때 어떤 문장인지 정확히 짚어내는 능력(정밀도와 재현율)은 0.3~0.5 수준입니다. 이 때문에 오차가 커질수록 감점을 줄이고, 160px 수준에서는 감점을 보류합니다.

## 바뀐 판정 방식

| 항목 | 이전 | 이후 | 이유 |
|---|---|---|---|
| 고정 검출 분산 기준 | 120px 고정 | `max(120, 6 × 흔들림)` | 흔들림이 크면 하나의 고정이 여러 개로 쪼개져 체류 시간이 사라졌습니다. |
| 문단 상자 세로 여유 | 18px | `max(18, 0.5 × 보정 오차)` | 오프셋 때문에 문단 밖에 떨어진 고정이 버려졌습니다. |
| 다시 읽기 | 이전 문장에 2번 이상 다시 들어옴 | 지금까지 읽은 가장 아래 줄보다 **2줄 이상 위**로 가서 **0.5초 이상** 머문 경우 1번 이상 | 한 줄 정도의 흔들림은 다시 읽기로 세지 않습니다. 가장 아래 줄 위치도 최근 고정 3개의 중앙값으로 정해, 튀는 고정 하나에 흔들리지 않습니다. |
| 느린 문장 | 단어당 시간이 본인 중앙값의 1.75배, 3단어 이상 | 2.0배, 5단어 이상 | 짧은 문장은 잡음에 따른 시간 편차가 큽니다. |
| 단어 후보 | 항상 | 보정 오차 40px 이하일 때만 | 단어 하나를 가리려면 반 줄 이내의 정확도가 필요합니다. |
| 감점 적용 | 항상 100% | 보정 오차 60px까지 100%, 150px에서 0%가 되도록 선형 감소 | 신뢰할 수 없는 측정으로 점수를 깎지 않습니다. 계산상 감점(`raw_penalty`)은 교사 화면에 남깁니다. |

흔들림은 보정 단계에서 점을 응시하는 동안 샘플이 흩어진 정도(MAD 기반 표준편차)로 측정합니다.

## 시도했지만 넣지 않은 것

**DTW 기반 세로 드리프트 보정**: 시선 순서를 줄 순서에 동적 계획법으로 맞춰 오프셋을 추정하는 방법입니다. 줄이 같은 간격으로 반복되다 보니, 오프셋을 추정하는 대신 "한두 줄 아래 줄"에 맞춰 버려서 효과가 없었습니다. 문헌에 나오는 return sweep 분할 방식(줄 끝에서 줄 처음으로 크게 돌아가는 시선을 기준으로 나누기) 같은 줄 배정 알고리즘을 실제 데이터와 함께 검토할 만합니다.

## 다음 단계: 실제 데이터로 확인

1. 실제 웹캠으로 세션을 모읍니다. 학생 여러 명이 지문을 2~3개씩 읽습니다.
2. 결과 화면에서 학생이 실제로 어려웠던 문장을 직접 표시합니다. 자동 감지된 문장은 미리 표시돼 있으므로, 해제했는지까지 정답 데이터로 씁니다.
3. 자동 감지와 학생 표시가 얼마나 겹치는지 보고, `AnalysisParams` 값을 조정합니다.
4. 대시보드의 **전체 다시 분석**(또는 `python -m backend.reanalyze`)으로 저장된 세션 점수를 새 기준에 맞춰 다시 계산합니다.

시뮬레이션의 한계도 있습니다. 실제 웹캠 오차는 화면 위치마다 다르고, 머리를 움직이면 갑자기 바뀝니다. 여기서는 고정 오프셋 하나로 단순화했는데, 보정의 아핀 변환이 고정 오프셋을 상당 부분 제거하므로 실제보다 비관적인 가정입니다.
